# honyakuchou-lint — 翻訳調・AI臭の検出と具体化

## なぜこのスキルがあるか

ユーザーの原体験はこれ。

> 「抽象的なものを主語にして乗る・立つ・担う・働く・回す・置くを使うと超AIって感じする。俺の気持ち悪さはこれだった」（2026-08-10）

ただし**語を禁止しても直らない**。「担う」を禁じれば「支える」「機能する」に逃げるだけで、モグラ叩きになる。気持ち悪さの本体は語ではなく、次の4条件が重なった状態にある。

1. 抽象語が何を指すか曖昧（「この設計思想が」＝誰の何？）
2. 動詞が事実を具体化せず、比喩で済ませている（「効いている」＝何がどう変わった？）
3. 同種の比喩が短い範囲で連鎖する（配置→回転→起立→移動が1段落に同居）
4. 行為者が消える（「指標が判断を担う」＝判断しているのは人のはず）

だから検出単位は語ではなく **抽象度 × 共起の自然さ × 比喩密度 × 情報圧縮度**。単独なら自然な「バイアスが働く」を全滅させると、代わりに幼い文章ができあがる。狩るのは過剰な個体だけ。

## 最重要原則：具体化は「戻す」であって「作る」ではない

このスキルで一番事故りやすいのがここ。「抽象的に書くな」と指示された書き手は、**具体を発明して埋める**方向に走る。

```
悪:  このデータが意思決定を支える。
NG改善: 担当者はこのデータから解約率を確認し、継続する施策を決める。
        └ 解約率も継続施策も、元原稿のどこにも書いていない。AI臭は消えたが嘘が増えた
OK改善: 担当者はこのデータを見て判断する。
        └ 消えていた行為者（担当者）だけを戻した。増やしていない
```

具体化とは、比喩によって**隠されていた情報関係を復元する**操作。素材に無いものは復元できない。素材が無いときの正しい着地は3つだけ。

- **人を主語に戻す**（「信頼が積み上がる」→「読者が少しずつ信じてくれるようになる」）
- **字義的な動詞で言い直す**（「役割を担う」→「〜を決める」「〜を義務づける」）
- **`〔要確認：誰が何を〕` を残して報告する**（推測で埋めない）

判定テスト＝**書き換え後の文に、書き換え前に無かった固有名詞・数字・因果が入っていないか。** 入っていたらそれは具体化ではなく捏造。

## 工程

```
Phase 0  ジャンル判定と強度設定
Phase 1  候補抽出（scripts/lint.py）
Phase 2  0〜3分類（references/shindan-hyou.md）
Phase 3  リライト（references/rewrite-recipes.md・2と3だけ）
Phase 4  再測定と報告
```

### Phase 0｜ジャンル判定と強度設定

先にジャンルを決める。同じ「比喩1個」でも、セールスレターと業務報告書では意味が正反対だから。**判定せずに一律適用すると、物語で読ませる原稿の背骨を折る。**

| ジャンル | 抽象主語＋比喩動詞 | 比喩鎖 | 比喩そのもの | 備考 |
|---|---|---|---|---|
| セールス本文（LP/レター/ステップメール/VSL） | 厳しく狩る | 厳しく狩る | **殺さない** | 読者を動かす比喩・情景は資産。狩るのは「抽象主語で行為者が消えた文」だけ |
| 解説レポート・教材・ビジネス文書・提案書 | 最も厳しく | 最も厳しく | 1段落1個 | レポートが本来想定している領域。ここが一番効く |
| YouTube台本・ナレーション | 厳しく狩る | 厳しく狩る | 耳基準 | 判定軸が変わる＝**聞いて絵になるか**。目で読めば分かる抽象語も、耳では消える |
| SNS短文（X/Threads/IG） | 中 | 該当しにくい | 自由 | 短いので密度指標は使わない。行為者消失だけ見る |
| 案件ノート・議事録・仕様 | 中 | 中 | 抑制 | 「誰が何をいつまでに」が消えていたら致命的 |

### Phase 1｜候補抽出

```bash
python ~/.claude/skills/honyakuchou-lint/scripts/lint.py <対象ファイル>
```

対象動詞の近傍に抽象語がある文を機械的に拾い、行番号・密度・比喩鎖の位置を出す。目で探すと必ず漏れる（書き手は自分の文体が見えない）。

このスクリプトは**候補を出すだけで、良し悪しを判定しない**。日本語は主語省略とゼロ照応が多く、正規表現で「抽象主語」を確定させることは原理的にできない。判定はPhase 2で人／モデルがやる。ここを混同して「ヒット＝悪」にすると、「電車に乗る」まで直しにいく。

複数ファイルをまとめて測るとき、JSON出力で受けたいときは `--json`。密度の基準線を自分の合格原稿から取るときは `--baseline` を付けて過去の良い原稿を測る（下記「密度基準の較正」）。

### Phase 2｜0〜3分類

`references/shindan-hyou.md` を実読して、候補を1件ずつ4段階に振る。**直すのは2と3だけ。** 1（自然な慣用）は密度が超過しているときだけ間引く。

| ラベル | 意味 | 例 |
|---|---|---|
| 0 | 字義的用法。触らない | 電車に乗る／箱を置く |
| 1 | 自然な慣用。原則そのまま | バイアスが働く／中心に置く |
| 2 | 不要に抽象的。具体化すべき | この指標が判断を担う |
| 3 | 過剰・連鎖・強いAI感 | 問いを起点に置き、議論を回し、結論を軌道に乗せる |

この4段階を挟む理由は、全件リライトを避けるため。全部直すと文章が説明書に退化する。

### Phase 3｜リライト

`references/rewrite-recipes.md` を実読し、型別のレシピで書き換える。素材（元資料・事実台帳・前工程の原稿）が手元にあるかどうかで**A系統／B系統**を切り替える。この切り替えを飛ばすと捏造が始まる。

- **A系統（素材あり）**：素材に書いてある主体・数字・出来事に置き換える
- **B系統（素材なし）**：人を主語に戻す／字義動詞で言い直す／`〔要確認〕`を残す

書き換えたら**元の文と並べて残す**。ユーザーが「前の方が良かった」に戻れる状態を保つ。特にセールス本文では、具体化が感情の熱を下げることが普通にある。判定はユーザーがする。

### Phase 4｜再測定と報告

もう一度 `lint.py` を回して、密度と比喩鎖が下がったことを数字で確認する。報告はこの形。

```
翻訳調リント結果：<ファイル名>（ジャンル：解説レポート）
  本文 4,120字／候補 14件 → 5件／密度 3.4 → 1.2件/1000字
  比喩鎖 3箇所 → 0箇所
  内訳：3が2件・2が7件を書き換え、1が5件は残置（慣用のため）
  〔要確認〕を2箇所残しました（L88／L134）— 素材に主体が無いため推測しませんでした
```

`〔要確認〕`が残ったら必ず本文で報告する。黙って残すと、そのまま公開されて意味不明な原稿になる。

## 密度基準の較正

初期値は **2以上の候補が1,000字あたり1件以下／比喩鎖ゼロ**。ただしこれは運用開始用の仮の数字で、根拠のある標準値ではない。

実運用では**自分の合格原稿で較正する**のが正しい。過去に「これは良い」と判断した原稿を3本 `--baseline` で測り、その平均を基準にする。ジャンルによって自然な比喩密度はまったく違うので、他人の閾値を借りても意味がない。較正結果は `references/baseline.md` に追記して育てる（無ければ作る）。

## 禁止事項

- ❌ 対象動詞を一括置換する（「担う」→「果たす」等の機械的な語の入れ替え。同じ構文が別の語で残るだけ）
- ❌ 素材に無い固有名詞・数字・因果を書き足して「具体化した」と称する（このスキル最大の事故）
- ❌ ジャンル判定を飛ばして一律適用する（セールス本文から比喩を抜くと売れなくなる）
- ❌ ラベル1（自然な慣用）を密度超過でもないのに直す
- ❌ 原文を残さずに上書きする
- ❌ 文体以外の検品を名乗る——事実照合・景表法は軍配 `review-protocol`、切れ味・仕様遵守は `model-independent-quality`。潰し合わないので**併走させる**

## 隣接スキルとの切り分け

- **copy-studio**：本文を書く工程そのもの（セールス限定・サブエージェント隔離執筆）。本スキルはその検品側で、`writing-rules.md` A8 の実行部にあたる。copy-studio Phase 3 の検品から呼ばれる
- **gutaika-trainer**：ユーザー本人の言語化を問いで鍛える稽古。原稿は直さない。本スキルは原稿を直す。「自分の表現力を上げたい」→trainer、「この原稿を直して」→本スキル
- **model-independent-quality**：P8として本スキルを参照する。あちらが総合検品、こちらが翻訳調の専任

## ファイル構成

- `scripts/lint.py` — 候補抽出・密度・比喩鎖の機械検出（Phase 1・4で実行）
- `references/shindan-hyou.md` — 0〜3の判定基準・検出語彙・「直さない」慣用リスト（Phase 2で実読）
- `references/rewrite-recipes.md` — 型別の変換レシピ（A系統／B系統）とジャンル別注意（Phase 3で実読）
- `references/baseline.md` — 較正した密度基準の台帳（運用しながら育てる）
